# T5.3 — NeoPixel → RMT LED strip driver (`uc2_pixel_buf`) (D2)

**Phase 5 · Effort 2–4 d · Depends: T4.8 · Gated by: D2**
**Invariants:** dual-build; pixel timing identical (WS2812 bit timings are hard). Index: `../PORT_PLAN_STEPS.md`

## Goal
Replace the Adafruit NeoPixel C++ lib (used by xiao_odmr, canopen_led, the S3 WS2812
path) with a C driver on the same RMT pattern `Ws2812Rmt` already uses — one WS2812 code
base instead of two.

## Actions
1. Write `components/uc2_pixel_buf/led_strip_ws2812.c` (RMT TX, 800 kHz WS2812 timing,
   GRB order) — model it on `Ws2812Rmt`'s proven tables (same chip, same RMT driver);
   keep the existing `uc2_pixel_buf` public API so `main/` callers don't change.
2. Point the NeoPixel-using boards at it: `xiao_odmr`, `canopen_led` (S3 WS2812 path),
   any other `UC2_LED_CONTROLLER` board currently using NeoPixel (audit via
   `grep -rn "Adafruit_NeoPixel" components/`).
3. **Classic ESP32 vs S3**: Ws2812Rmt has chip-specific tables; if the new driver is
   cleaner, optionally also replace Ws2812Rmt's role — but that's T5.4 territory; this
   step must not regress T2.1/T3.4 boards.
4. `[HW]` pixel check: identical pattern render on one S3 board (canopen_led or
   xiao_odmr) and one classic board (uc2_4 — FAS coexistence!).

## Acceptance
- NeoPixel lib deleted from the component set (grep empty); `[HW]` pixel checks pass on
  both chip families; `make test` green; sizes in budget.

## Rollback
Keep NeoPixel as the documented C++ leaf exception (D2) until the driver is stable; the
public API means the board code doesn't move.

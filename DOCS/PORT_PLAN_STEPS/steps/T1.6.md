# T1.6 — Port the laser app to direct IDF

**Phase 1 · Effort 1–2 d · Depends: T1.5 · Gated by: —**
**Invariants:** IDF-only (no PIO); size ±10 %. Index: `../PORT_PLAN_STEPS.md` · Layout: `../refs/component-layout.md`

## Goal
The laser app's full source set compiles + links with direct IDF calls — **no per-controller
refactoring yet** (that split is T1.9, needed only once a 2nd app shares components).

## Approach (what was done)
The laser app uses an **app-local `uc2_modules` component** (`apps/canopen_slave_laser/components/
uc2_modules/`) that compiles the module TUs straight from `main/src/<module>/`, with
`INCLUDE_DIRS = main/ + every main/src/<module>/`. The app's `main.c` is a thin entry
(`app_main() → uc2_app_start()`); the real `setup()/loop()` glue is `components/uc2_app/main.cpp`.
The glue headers (`cJsonTool.h`, `PinConfigDefault.h`, `JsonKeys.h`) live in `components/uc2_app/`
and are exposed via that component's `INCLUDE_DIRS` — so module files `#include "cJsonTool.h"`
bare. Relative includes (`#include "../config/ConfigController.h"`) resolve within `main/src/`.

This keeps the port **compile-level** (no module moves), matching the original T1.6 goal.

## Rules (important)
- Fix per-file compile errors by **converting to direct IDF** (new Arduino APIs discovered →
  convert to IDF equivalent + record in `../refs/arduino-idf-mapping.md`), NOT by refactoring modules.
- Do not change protocol bytes or control logic — this is a compile-level port.
- `#include "PinConfig.h"` resolves via the app's include dir (T1.5).

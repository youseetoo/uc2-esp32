# UC2-ESP32: Port to C + ESP-IDF — Plan (v2, verified against repo 2026-07-24)

> **SUPERSEDED (2026-10):** the active plan is [`PORT_PLAN_STEPS.md`](PORT_PLAN_STEPS.md) —
> pure ESP-IDF 6.1, **no shim layer** (this doc's `uc2_hal` shim approach was dropped in
> favor of converting `main/` to direct IDF calls, T1.3) and PIO retired (T6.3–T6.6).

Goal: move the firmware off PlatformIO + Arduino (Arduino-ESP32 2.0.15/2.0.17, i.e. ESP-IDF 4.4.2)
onto **native ESP-IDF**, and convert the first-party code from **C++ to C**.

Two independent workstreams, deliberately sequenced:

1. **Build system first** (PlatformIO/Arduino → ESP-IDF), keeping the code C++ behind a thin
   compatibility shim. This gets every board building and flashing under `idf.py` with minimal
   code churn and a working regression baseline.
2. **Language second** (C++ → C), module by module, against a stable IDF build.

The codebase is very C-friendly: no inheritance, no virtuals, no templates. "Classes" are
either static-method namespaces (`CANopenModule`, `SerialProcess`, …) or POD structs with inline
methods (`AxisPID`). `std::` usage is minimal (`std::string` in 1 file: `BtController.cpp`;
`std::map` alongside it). The C conversion is therefore a mechanical refactor, not a rewrite.

## 1. Current state (verified)

- **Build**: PlatformIO, `framework = espidf + arduino`, Arduino-ESP32 2.0.15 (IDF 4.4.2) or
  2.0.17, platform-espressif32 v6.3.2/6.9.0. `src_dir = main`.
- **Environments**: 21 envs in `platformio.ini`: **17 built in CI**
  (`.github/workflows/build-and-release.yaml`: UC2_2/3/4/WEMOS, xiao ODMR/ledservo/ledring,
  canopen slaves motor/accelmotor/galvo/laser/led/gpio, canopen ps4-usbhost bridge, canopen
  master, canopen standalone v4, waveshare ledarray) + 4 dev-only: `esp32dev`, `m5stack_dial`,
  `waveshare_esp32s3_7inchScreen`, `UC2_canopen_bridge_ptz`.
- **CI (4 workflows)**:
  - `build-and-release.yaml` — 17-env matrix → esptool `merge_bin` (bootloader+partitions+boot_app0+firmware)
    into one `.bin`/board + manifest JSON; GitHub Release; mirrors to `youseetoo/uc2-esp32-binaries`
    (jsDelivr CDN + Web Flasher). Build-system agnostic — only the "build firmware" step changes.
  - `build-frame.yaml` — builds the UC2_3, seeed_xiao_esp32s3 and UC2_canopen* envs, publishes a
    GHCR firmware image ("firmware-image-server", Dockerfile at repo root) + tag release.
    Its firmware-build step needs the same IDF treatment.
  - `build-odmr-external.yaml` — builds an **external** ODMR repo (its own PIO project).
    Not affected by this port.
  - `canopen-registry-check.yml` — Python drift check: regenerates EDS/OD.h/UC2_OD_Indices.h from
    `tools/canopen/uc2_canopen_registry.yaml` and fails on diff. No PIO dependency — keep as-is.
- **Code**: `main/src/` with **33 module dirs, 65 `.cpp` files** (+ headers):
  analogin/out, axis, bt, buzzer, canopen, config, dac, dial, digitalin/out, encoder, fan,
  gpio_can, heat, home, i2c, image, joystick, laser, led, message, motor, pid, ptz, qid,
  scanner, serial, signal, state, thermal, tmc, tmp102.
  - **~100 files include `Arduino.h`** (101 include lines: 28 `<Arduino.h>` + 73 `"Arduino.h"`);
    `Wire.h` in 9 files; `OneWire.h` in 2 (`DS18b20Controller`).
  - No inheritance, no virtual (0 matches), no templates; `std::string` in `BtController.cpp`
    only (PS4 HID parse) + one comment; `std::max/min` in a couple of spots.
  - Largest files: `canopen/CANopenModule.cpp` (**138.3 KB**), `motor/FocusMotor.cpp` (~31 KB),
    `serial/SerialProcess.cpp` (~28 KB), `main.cpp` (~25 KB).
- **Already C / IDF-friendly**:
  - `lib/ESP32_CanOpenNode` — CANopenNode in C; `CO_driver_ESP32.c` uses **IDF TWAI driver
    APIs + TWAI ISR directly** (no Arduino CAN).
  - `lib/uc2_od` — object dictionary in C, generated by `tools/canopen/regenerate_all.py`
    from `uc2_canopen_registry.yaml` (drift-checked by the registry workflow above).
  - `main/cJSON` — git submodule; **the only JSON library in the codebase** (used by
    `cJsonTool.h`/`JsonKeys.h` and the CANopen parts). **ArduinoJson is not used anywhere.**
  - `lib/esp_usb_host_hid` — USB HID host in C on IDF `usb_host`.
  - `main/src/led/Ws2812Rmt.cpp` — first-party **bare-metal WS2812 RMT driver** (writes
    `RMTMEM` with IRQs off, no IDF RMT driver, chip-specific RMT structs for ESP32 vs S3).
    This is the real push path for all NeoPixel strips — kept because FastAccelStepper
    (gin66) owns the shared RMT IRQ and a second `rmt_driver_install()` would fight over it.
    Implication: RMT channel allocation (FAS owns 0..3 on UC2_4; WS2812 on 4 or 0) is an
    integration constraint to preserve.
- **Vendored / registry C++ libs actually used in `main/`**:
  - **FastAccelStepper** (71 references; performance-critical stepping + RMT ownership),
  - **TMCStepper** (I2C driver, C++ class surface), **youseetoo/AccelStepper** (URL fork,
    accelmotor env),
  - **ESP32Encoder 0.12.0** (PCNT; axis/encoder/dial),
  - **RobTillaart TCA9555** (registry; first-party wrappers `tca_controller`/`tca9535`),
  - **OneWire + DallasTemperature** (registry; DS18b20 heat controller),
  - **Adafruit NeoPixel** (registry; used as the **pixel data buffer** only — `begin()`/`show()`
    are bypassed in favor of `Ws2812Rmt`; Adafruit BusIO/GFX are transitive, not included
    directly in `main/`),
  - **M5Unified + M5GFX + M5Dial** (registry; **`m5stack_dial` env only** —

  - **PSController** (`lib/`, C++ on Arduino BLE — the PS4 path),
  - **DAC_Module** (`lib/`), **AS5311-PWM** and **ESP32-TWAI-CAN-master** (`lib/`,
    **not referenced by `main/`** — see below).
- **In `lib/` but unused by `main/`** (delete or keep, no build impact):
  `ESP32-TWAI-CAN-master` (CANopenNode's driver already uses IDF TWAI directly),
  `AS5311-PWM` (only a comment in `main/config/UC2_4/PinConfig.h`).
- **Config plumbing**: per-env `PinConfig.h` copied by `tools/copy_PinConfig.py`

  **96 `sdkconfig*` files** at repo root (incl. the 50 KB `sdkconfig.defaults` and many stale

- **Partial IDF work already exists** (current branch `main_espidf`): 3-line top-level

```
│  ├─ uc2_hal/                  # Phase-A shim: millis/digitalWrite/Wire/Serial/log on IDF
│  ├─ canopen_node/             # from lib/ESP32_CanOpenNode (C, as-is)
│  ├─ uc2_od/                   # from lib/uc2_od (C, as-is; codegen untouched)

│  ├─ esp_usb_host_hid/         # from lib/ (already IDF-based)

│  ├─ tmc_stepper/  onewire_ds18b20/  tca95xx/
│  ├─ encoder/                  # from ESP32Encoder 0.12.0 (PCNT-based)
│  ├─ neo_pixel_buffer/         # Adafruit NeoPixel kept as data buffer (or plain struct, §5)
│  └─ m5gfx/                    # only if the dial board is ported now (C++ leaf; §7)
├─ boards/                      # PinConfig.h per board (replaces main/config/* + copy script)
│  ├─ uc2_2/PinConfig.h
│  ├─ uc2_canopen_slave_motor/PinConfig.h
│  └─ ...
├─ apps/                        # one IDF app per env (replaces [env:*] in platformio.ini)
│  ├─ uc2_2/                    # CMakeLists.txt + main.c + sdkconfig.defaults + board link
│  ├─ uc2_3/  uc2_4/  uc2_wemos/
│  ├─ xiao_odmr/  xiao_ledservo/  xiao_ledring/
│  ├─ canopen_master/  canopen_standalone_v4/
│  ├─ canopen_slave_motor/  canopen_slave_accelmotor/  canopen_slave_galvo/
│  ├─ canopen_slave_laser/  canopen_slave_led/  canopen_slave_gpio/
│  ├─ canopen_bridge_ps4_usbhost/  canopen_bridge_ptz/
│  ├─ waveshare_ledarray/
│  └─ (optional) m5stack_dial/  waveshare_7inch/     # M5GFX decision (§7)
├─ test/                        # host tests (native) + IDF component tests (Unity, in C)
├─ tools/                       # canopen codegen, copy_PinConfig (retired), etc.
└─ partitions/                  # custom_partition*.csv (moved from root)
```

Notes:

- `main/src/led/Ws2812Rmt` stays **first-party** (it's the actual RMT push path) — it folds
  into `uc2_led`/the motor-bearing components rather than becoming a "vendor" component.
- No web server component: **there is no ESPAsyncWebServer/LVGL usage in `main/`** (0
  matches); `LV_CONF_INCLUDE_SIMPLE` in the 7"-screen env is a transitive M5GFX knob.

Per-app `CMakeLists.txt` pattern (replaces the `-DCONFIG=…`/feature-var CMakeLists trick and
the `copy_PinConfig.py` pre-step):

```cmake
idf_component_register(SRCS "main.c" INCLUDE_DIRS "."
                       REQUIRES uc2_core uc2_serial uc2_canopen …)
```

Feature selection (MOTOR_CONTROLLER, LASER_CONTROLLER, …) becomes the app's own
`sdkconfig.defaults` + Kconfig symbols, so each board is a first-class IDF app with no
shared-source-conditional-CMake.

## 3. Phases

### Phase 0 — Baseline & decisions (1–2 days)

1. Capture a regression baseline per env before touching anything:
   - `pio run -e <env> -t size` (flash/RAM) for all 17 CI envs → `DOCS/baselines.md`.
   - Serial protocol smoke captures (JSON get/act round-trips) and one CANopen bus trace
     (master + one slave) for later A/B comparison.
2. Record decisions (open items in §7): IDF version, strictness of C, board scope,
   M5GFX boards, test-suite adoption, dual- or hard cutover.
3. Continue on the `main_espidf` lineage (branch `port/idf-c` off it).

**Accept**: baseline committed; decision list resolved in writing.

### Phase 1 — IDF skeleton + first app (2–4 days)

1. Distill a real `sdkconfig.defaults` baseline (the current one is a 50 KB dump — reduce to
   explicit choices: partition size, TWAI, USB, BLE settings, log levels) + per-target overlays.
2. Create `components/`: move `lib/ESP32_CanOpenNode`, `lib/uc2_od`, `main/cJSON`,
   `lib/esp_usb_host_hid` verbatim with `idf_component_register` + `CMakeLists.txt`
   (they are already C / IDF-native — near-zero effort).
3. Build **`uc2_hal` shim v1** mapping the Arduino API surface actually used:
   `millis/micros/delay/delayMicroseconds`, `digitalWrite/digitalRead/pinMode/touchWrite`,
   `noInterrupts/Interrupts`, `Serial` (→ IDF UART driver), `Wire` (→ IDF I2C master v2),
   `log_i/log_w/...`, `constrain/abs/min/max`, `attachInterrupt`, `analogWrite` (LEDC).
   This lets existing `.cpp` files compile with minimal edits.
4. Scaffold **app #1: `canopen_slave_laser`** (smallest feature set: LASER_CONTROLLER +
   DIGITAL_IN_CONTROLLER + MESSAGE_CONTROLLER + CAN; no BT, no motors, no display):
   `main.c` with `app_main()`, loop moved to a periodic task (or keep the app's existing
   FreeRTOS tasks), PinConfig from `boards/`. Note: `main.cpp` is shared by all envs and
   feature-gated, so the core chain (State, Config, SerialProcess, QidRegistry, Endpoints)
   must compile for app #1 either way.
5. Port the laser module + message controller + `uc2_core` state/config onto the shim.
6. CI: add a second job building `apps/canopen_slave_laser` with `idf.py` alongside the
   existing PIO job (dual-build gate for the rest of the port).

**Accept**: `idf.py build` + flash; laser toggles via serial JSON; CANopen node reaches
OPERATIONAL under a master; flash/RAM within ~10 % of the PIO baseline.

### Phase 2 — All non-BT boards under IDF (1.5–3 weeks)

1. Port remaining modules onto shim + components: `uc2_serial` (SerialProcess + Endpoints),
   `uc2_motor` (FocusMotor, AxisPID, homing, stage scan, PID), I2C peripherals
   (TCA9555/9535, DAC_Module, TMP102, MCP4822 SPI galvo DAC), `uc2_canopen`
   (CANopenModule 138 KB: SDO/TPDO/RPDO sync, streaming-SDO OTA, gpio_can, PTZ, device router),
   led (NeoPixel buffer + Ws2812Rmt), heat (DS18b20), fan, digital in/out, encoder, tmc.
2. Replace remaining Arduino-isms:
   - `Wire` users (9 files) → shared I2C bus helper (one master per bus, multi-device).
   - `std::string`/`std::map` in `BtController.cpp` → heap/fixed buffers (handled in Phase 3).
   - `Adafruit NeoPixel` → keep as a plain pixel-buffer struct; `Ws2812Rmt` (already
     first-party) stays the only push path. Drop the NeoPixel dependency entirely if the
     buffer API is small (recommended — verify first).
   - JSON: nothing to migrate — cJSON is already the only JSON lib.
3. Create the remaining apps: all 17 CI envs + `canopen_bridge_ptz` (1:1 mapping in §4).
4. Cleanup: delete stale `sdkconfig.*` files and stale `main/config/*` dirs not matching a
   live env (45 config dirs → ~21); move partition CSVs; remove unused `lib/`
   (ESP32-TWAI-CAN-master, AS5311-PWM) or park them in `lib_legacy/`.

**Accept**: every CI env builds under `idf.py`; per-board smoke checklist passes
(serial protocol + CANopen + per-controller checks); sizes within budget.

### Phase 3 — Bluetooth envs (1–2 weeks; highest risk)

1. Inventory the PS4 path: `lib/PSController` (C++ on Arduino BLE) + `main/src/bt/`
   (DS4 trackpad extended-mode reports, `esp_hid_gap.c`), plus `UC2_FORCE_BT_CLASSIC_ONLY`
   semantics.
2. Port to the IDF BLE host: evaluate **Bluedroid vs NimBLE** for classic/BLE HID device
   emulation; pick per RAM budget (ESP32 master is RAM-tight; the internal-RAM headroom
   configuration from the PIO build must be reproduced in `sdkconfig`).
3. `canopen_bridge_ps4_usbhost`: keep `esp_usb_host_hid` (already IDF) — just wire it in;
   C-ify if it has C++ bits.

**Accept**: PS4 over BT pairs and sends input (incl. trackpad) on UC2_2/3/4 and canopen
master; USB-HID bridge env works; RAM headroom verified (`heap_caps_get_free_size` logged).

### Phase 4 — C conversion of first-party code (2–4 weeks, parallelizable)

Mechanical, module by module, leaf-first:

1. `pid/`, `axis/`, `signal/`, `state/`, `config/` (pure math/state — cleanest starts;
   AxisPID is already a POD struct).
2. `uc2_core`, `uc2_serial` (SerialProcess, Endpoints, JSON endpoints).
3. `uc2_motor` (FocusMotor, homing, scanner) + `Ws2812Rmt` (bare-metal C-style already —
   drop the `.cpp` wrapper, keep RMT channel allocation comments).
4. `uc2_canopen` (split CANopenModule.cpp along the way: `canopen.c`, `canopen_sdo.c`,
   `canopen_tpdo.c`, `canopen_ota.c`, `canopen_gpio.c`).
5. `main.cpp` glue → per-app `main.c`.

Rules:
- `class X { public: static … }` → `X_api.h` (functions with `x_` prefix) + `X.c`.
- POD classes with members → `typedef struct` + accessor/init functions; drop in-class
  method bodies.
- Keep per-component public C headers; no C++ features in any `uc2_*` component.
- CI gate: a job compiles all `uc2_*` sources as C (`-x c -std=c99`, host-side or as a
  separate component build) so C++ creeps in loudly.

**Accept**: zero C++ syntax in `uc2_*` components; all Phase-2 board checks re-pass;
host unit tests pass on the C code.

### Phase 5 — Vendor libraries (1–4 weeks, parallelizable)

- **C-ify (small, low risk)**: TCA9555/9535 wrappers, DAC_Module, youseetoo/AccelStepper,
  ESP32Encoder 0.12.0 (PCNT-based), OneWire/DallasTemperature (small; removes two registry
  deps), PSController wrapper surface (core ported in Phase 3).
- **Keep as C++ leaf components** (recommended, isolate behind a 1-file C backend header):
  **FastAccelStepper** (performance-critical, owns the shared RMT IRQ — do not rewrite
  without evidence), **TMCStepper** (I2C driver; C++ only at the class surface).
- **M5GFX/M5Unified/M5Dial** (m5stack_dial, waveshare 7"): open decision (§7). Options:
  keep these two boards on the PIO build until later, port M5GFX as a C++ leaf component,
  or replace the UI with a lighter C stack.

**Accept**: only the explicitly chosen leaf components remain C++; all in-scope boards build.

### Phase 6 — Tests, CI, docs (1 week, overlaps 4–5)

1. **CI**:
   - `build-and-release.yaml`: replace the PIO matrix with an `idf.py` matrix. Runner:
     espressif IDF GitHub action / Docker image or a self-hosted runner with IDF 6.1.
     Per app: `idf.py set-target esp32|esp32s3 && idf.py build`. Keep the existing esptool
     `merge_bin` step, manifest generation, GitHub Release, and binaries-repo mirror jobs
     unchanged.
   - `build-frame.yaml`: same firmware-build swap for its env subset; GHCR image + release
     jobs unchanged.
   - `build-odmr-external.yaml`: **unchanged** (external repo).
   - `canopen-registry-check.yml`: **unchanged** (already build-system agnostic).
   - Add jobs: `make canopen-check` (codegen drift — already in the workflow), C-only
     compile gate, host tests.
2. **Tests**:
   - Port the native host tests (`test/native/run.sh`) — keep C++11 for host-only use or
     C-ify the harness (acceptable either way).
   - Decide: adopt the **168-test Unity suite from `main_pioclean_mocks_tests`**
     (port to IDF component tests, `pytest`-driven, in C) vs re-derive a smaller suite.
     Adopting is recommended — mocks for CANopen/TWAI already exist there.
   - `main/testFeedbackStepper` (standalone rig): keep on PIO or convert; low priority.
3. **Docs**: README + `FLASH_SEEED_XIAO_ESP32S3.md` + developer docs updated to `idf.py`
   commands; delete `platformio.ini` (or keep as reference in a `legacy/` dir) at cutover.

**Accept**: green CI for all in-scope boards; a tag produces the same artifacts as before
(verified by the Web Flasher flow).

## 7. Open decisions (need user input before Phase 1)

1. **IDF version**: 6.1 (already installed at `M:\.espressif\v6.1\esp-idf`, GrowControl
   precedent) vs 5.5.x LTS (bigger community track record). **Recommend: 6.1.**
2. **Strictness of "C"**: (a) 100 % C incl. rewriting FastAccelStepper/TMCStepper backends
   (largest cost, risk to motor timing + RMT IRQ ownership), vs (b) C core + small set of
   C++ leaf components behind C backend headers. **Recommend: (b)**, revisit leaves later.
3. **Board scope**: all 21 envs (17 CI + ptz + m5stack_dial + 7" screen; esp32dev is
   dev-only), or a subset of boards still actually shipped?
4. **M5GFX boards** (m5stack_dial, waveshare 7"): keep on PIO temporarily, port M5GFX as a
   C++ leaf, or replace the UI stack?
5. **Test suite**: adopt the 168-test Unity suite + mocks from `main_pioclean_mocks_tests`
   (recommended) vs re-derive a smaller one.
6. **Cutover strategy**: dual-build CI (pio + idf side by side, timeboxed) vs hard cutover
   per board. **Recommend: dual-build**, retire a board's PIO env only when its IDF app is
   verified on hardware.
7. **Repo shape**: keep one repo with `apps/` (recommended; release pipeline stays one
   workflow) vs split firmware repos.

## 8. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| IDF 4.4 → 6.x driver deltas (I2C v2, RMT v5, TWAI, NVS) | build/runtime surprises | Phase 1 proves the stack early with the simplest app; per-app sdkconfig.defaults reviewed explicitly |
| CANopenModule.cpp (138 KB) | big-bang change | split into per-concern files during Phase 4; OTA/streaming-SDO gets its own test |
| BT RAM on ESP32 (master env) | PS4/HID regressions | reproduce `UC2_FORCE_BT_CLASSIC_ONLY` sdkconfig knobs; log free internal heap in smoke test |
| RMT channel allocation (FAS owns shared RMT IRQ; WS2812 on 4/0) | step-pulse corruption / LED strip latching | keep Ws2812Rmt as-is (bare-metal, IRQ-off); don't introduce a second RMT driver; compare vs baseline traces |
| Ws2812Rmt chip-specific RMT structs (ESP32 vs S3) | porting bug on one target | build both targets in Phase 2; LED slave + ledarray envs cover both chips |
| FastAccelStepper timing under shim/C | motor behavior drift | keep FAS C++ leaf; compare step timing vs baseline traces before touching |
| M5GFX size vs ESP32-S3 RAM | dial/7" boards don't build | §7 decision before touching them; they stay on PIO meanwhile |
| Dual-maintenance sprawl | schedule slip | timebox dual-CI; per-board retirement checklist |
| 96 stale sdkconfig* + 45 stale config dirs | confusion | cleanup task in Phase 2 (delete what no env references) |

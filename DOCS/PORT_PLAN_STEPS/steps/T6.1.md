# T6.1 — Per-board cutover, wave 1: non-BT, low-risk boards (D6)

**Phase 6 · Effort 1–2 d · Depends: T5.5 · Gated by: D6 (dual-build cutover confirmed), each board's T2.12/T3.8 retirement checklist**
**Invariants:** a board is cut over ONLY when its 4-item checklist (`refs/ci-cutover.md` §4) is fully ticked. Index: `../PORT_PLAN_STEPS.md` · Mechanics: `../refs/ci-cutover.md`

## Wave-1 board set (all Phase-2 boards, already smoke-proven)
`xiao_ledservo`, `xiao_ledring`, `waveshare_ledarray`, `canopen_slave_gpio`,
`canopen_slave_led`, `canopen_slave_galvo`, `canopen_slave_accelmotor`,
`canopen_slave_motor` (5 axis variants), `canopen_bridge_ptz`,
`canopen_bridge_ps4_usbhost`, `xiao_odmr`.

## Actions (per board, one commit each)
1. `build-and-release.yaml`: remove the board's PIO env from the release matrix; keep it
   in the `pio-build` dev matrix **only if** other boards still need that env (envs are
   shared — e.g. `seeed_xiao_esp32s3` is xiao_odmr's env; check `refs/env-app-mapping.md`
   for env reuse before deleting a matrix row).
2. Release asset naming: the IDF artifact replaces the PIO one (same name pattern,
   `refs/ci-cutover.md` §1) — downstream tooling (ImSwitch OTA, flash scripts) must not
   see a name change.
3. Tag a test release for the wave; verify the artifact set (count + names).
4. Tick the board's checklist "tagged release on hardware" item once the user confirms a
   flash on real hardware.

## Acceptance
- Wave-1 boards ship only from IDF builds; PIO matrix shrinks accordingly; release
  artifact set verified.

## Rollback
Per-board CI revert re-adds the PIO row (the PIO build still works — T6.6 hasn't deleted
anything yet).
